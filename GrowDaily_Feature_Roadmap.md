# GrowDaily — Feature Roadmap: Architecture Review & Build Order

*Covers Life Timeline, Monthly Story, Level System, Rooms-Alive, Beautiful Statistics, Journey Page, Milestone Celebrations, and Legacy Shelf. Written after a second pass through the live codebase specifically to find reuse points and risks before any implementation starts.*

## The one architectural decision everything else builds on

Four of your eight features — Monthly Story's "12 level ups," Journey Page, Milestone Celebrations, and Legacy Shelf's "Perfect Weeks ×18" — all need the same underlying thing: a timestamped log of "something meaningful just happened." Today that doesn't exist. `DashboardState` only stores current snapshots (level, streak, totalCompletions) with no history of *when* each one was crossed, which is exactly why your own spec flagged "12 level ups" as needing new logging rather than a hack.

Rather than four separate ad-hoc logs, I'd build one: a small `MilestoneEvent` model (`type`, `timestamp`, a small payload map) written to a new `users/{uid}/milestones/{id}` collection. `DashboardNotifier` already has one exact spot where it detects "level just increased," "streak just hit a threshold," and "an achievement just unlocked" (that's how `newlyUnlocked` and the celebration overlay in `reaction_overlays.dart` already work) — this is additive at that same detection point, not a parallel system: the instant those existing checks fire, they also drop one small doc in the new collection. Journey Page becomes a straight render of that collection grouped by month. Monthly Story's "12 level ups" becomes a date-range count against it. Legacy Shelf's "Perfect Weeks ×18" becomes a type-count query against it. One write path, four features fed. The only real risk is write volume for a very active user — worth logging coarse events only (level-ups, streak-threshold crossings, perfect days/weeks, achievement unlocks) and never per-habit-completion, which would turn this into a firehose.

## 1. Life Timeline — Approved, lifetime framing

Every number you listed already exists as a running total, with one real catch. `totalCompletions`, `totalGreenSquares`, `streak`, `longestStreak` (all on `DashboardState`) and `UserAccountModel.createdAt` ("Since July 2026" — exact, no new field needed) cover the headline stats directly. The heatmap block should reuse `dailyGreenCounts` plus the `heatColor`/`heatmapLevelFor` functions `MonthlyHeatmapScreen` already exports — same visual language the app already has, zero new rendering code.

The catch is your per-category lines — prayers, Quran sessions, workouts, charity. `HabitCategory.toJson()` deliberately collapses `quran`/`athkar`/`fasting`/`sadaqah` all down to the single stored string `'faith'` (and `fitness` to `'health'`) to keep Firestore's category field simple. That means a habit's *stored* category can't tell "Quran" apart from "charity" — both round-trip back as `HabitCategory.faith`. I checked, and the fix is clean: the Islamic catalog's own templates (`IslamicHabitCatalog.templates`) still carry the real, uncollapsed category (`quran`, `athkar`, `fasting`, `sadaqah`, `fitness` are set directly in that file, never serialized) — a habit's *own* `HabitModel.catalogId` field is enough to look the true category back up. So: for any habit with `isPreset == true`, resolve its category via the catalog template, not via `habit.category`; for user-created custom habits, fall back to their own (collapsed-but-that's-fine, since they were never Quran-specific to begin with) category directly. "Study sessions" has no matching catalog habit today, same way the original mockup's "21 books" didn't map to anything real — I'd bucket that one under `HabitCategory.learning` generically, catalog or custom.

Screen lives off Progress Hub, reads via `allHabitsEverProvider` (so archived habits still count, same reasoning `MonthlyHeatmapScreen` already uses). Free for everyone, as decided — no `premiumProvider` check anywhere in this screen.

## 2. Monthly Story — Approved, presentation layer only

Agreed: no separate data logic. The headline numbers reuse Life Timeline's exact aggregation, just filtered to the month's date keys within `dailyGreenCounts` — cheap, since that whole map is already loaded client-side (per `MonthlyHeatmapScreen`'s own doc comment, this is a display filter, not a new read). "12 level ups" and "never missed Fajr"-style lines are the two that need real support: level-ups come from the new Milestone Event Log described above; "never missed Fajr" needs a day-by-day scan of one specific habit across ~30 days, pricier than the rest of the card but still small at a monthly scope (this is exactly why I'd resist doing this at a yearly scope without the log — 30 day-docs is fine, 365 is not).

Export: capture the finished card via Flutter's standard `RepaintBoundary` + `toImage()` pattern, share via `share_plus` (already a dependency, already used for Room codes, already supports image attachments through `ShareParams`). No new packages needed for either the animation (`flutter_animate`, already everywhere) or the export.

## 3. Level System — Approved, separate prestige lane

Your reframe is the right one and matches what's already there: `HabitModel`/`CharacterState` already keep gold-purchases and always-free characters as two clean, separate lanes, so Levels becomes a third rather than a fork of either. One refinement worth flagging: last message I validated cosmetic-unlock spacing at 5/12/20/30/50, but your title thresholds this message are 5/15/30/50/75/100 — two different schedules. I'd collapse these into one: attach a cosmetic *and* a title to the same six levels (5/15/30/50/75/100) rather than running two separate unlock calendars a player has to track separately. Titles by themselves cost nothing new to compute (just a lookup table keyed by level, evaluated wherever level is already read).

The cosmetic list needs a scope split, because it's not all the same size of work. Profile frames, banners, and nameplate styles are the same shape as what `AccessoryCatalog` already does (a static catalog entry + an ownership check + a render slot) — small, precedented additions. Animated profile frames, avatar idle animations, and celebration animations are a different order of work: the character system today renders a single static PNG per character/accessory (`CharacterAvatar`, composited images, no animation runtime for the avatar itself) — "idle animation" and "animated frame" need either a sprite-sheet/Lottie-driven rendering path that doesn't exist yet, or scoping down to something like a shimmer/glow shader effect instead of true animation. I'd sequence static cosmetics first (fast, reuses everything) and treat animated cosmetics as a follow-up once you've decided the actual rendering approach — same "needs art/direction before engineering" flag as last message, now more specific about why.

For Rooms: today the leaderboard shows nothing about level at all (checked — no level field reaches `RoomParticipant`). Showing "⭐ Guardian / Ahmed / Lv. 43" needs `RoomParticipant` to carry a denormalized `level` field, refreshed the same way `characterId`/`displayName` already are (that's an established pattern here, not a new one — see `RoomParticipant`'s own doc comment on why character/name are snapshotted rather than looked up live). Title itself doesn't need its own stored field — derive it client-side from level via the same lookup table Profile uses, so there's only ever one source of truth for "what title does level 43 mean." Small, well-precedented change; the only real edit is `_LeaderboardRow` in `room_detail_screen_leaderboard_extend.dart`.

Not touching the XP curve, as instructed.

## 4. Rooms Should Feel Alive — Approved, phased as specified

**Phase 1.** `roomParticipantsProvider` and `roomProvider` are already live `.snapshots()` streams — confirmed, every client with a Room screen open is already getting real-time updates today, this part needs nothing new. The work is entirely client-side: keep the previous emission in state, diff against the new one, and classify what changed (someone's `dailyDoneCount` crossed into "done today," `currentStreak(room)` crossed a threshold, `teamCompletedToday`/`teamIsPerfect` flipped true). Celebrate with `showVictoryBurst`, already documented in this codebase as "the celebration language of the app." For streak milestones, reuse `GameConstants.streakBonuses`' existing keys (3/7/14/30/60/100) rather than inventing new ones — same "meaningful day" vocabulary the app already pays real XP bonuses against elsewhere, so a celebrated streak and a rewarded streak always agree. Gate on exactly those thresholds plus first-completion-of-the-day and team-100% — nothing fires on every single tap.

**Phase 2 — architecture only, not implemented.** The app has no `firebase_messaging` dependency and no Cloud Functions today, so this is real new infrastructure, not a config flag. Sketch: add `firebase_messaging` client-side, store each signed-in device's token on its `UserAccountModel` (refreshed via `onTokenRefresh`); add a Cloud Function with a Firestore `onWrite` trigger on `rooms/{roomId}/participants/{uid}`, diffing before/after the same way Phase 1's client-side logic already does, and on a celebration-worthy change, look up the other participants' tokens and send a multicast push via the Firebase Admin SDK. The trigger would want the exact same "what counts as celebration-worthy" rule Phase 1 already defines, ideally shared logic rather than reimplemented server-side — worth writing that classifier in a way that's portable (a pure function of before/after state) from the start in Phase 1, so Phase 2 can lift it rather than rewrite it.

## 5. Beautiful Statistics — Approved, treated as an initiative

Audit, as requested: heatmaps (`MonthlyHeatmapScreen`), color progression (Grid's entire premise), and calendar-style entrance animation (`flutter_animate`, already used throughout) are already built. What's genuinely new is two chart types — a "streak river" (a flowing custom-painted visual over existing streak history, pure presentation, no new data) and "habit evolution" (a trend line over time, which the Insights engine's `HabitPattern`/`InsightsResult` already computes the underlying scheduled-vs-completed numbers for — this would be a new chart on already-computed data, not a new analysis pipeline). I'd run this as an ongoing pass across Progress Hub and Monthly Heatmap rather than a single ship.

## 6. Journey Page — New, mostly free once the Milestone Event Log exists

Once section 0's log is in place, this is close to a pure rendering exercise: query `users/{uid}/milestones` ordered by timestamp, group by month, render one story-beat card per entry with an icon/color per `type` (reusing whatever visual language Milestone Celebrations settles on, see below, so the two features share one icon set instead of two). `flutter_animate` covers the reveal-as-you-scroll feel. The one thing this needs that the log alone doesn't provide automatically: a handful of *narrative* milestone types that aren't simple threshold crossings — "your first perfect week," "Ramadan 2027: never missed Fajr" — need their own explicit detection logic (a perfect-week check already has to exist for Monthly Story's "7 perfect days" anyway, so this is reuse, not new logic; a Ramadan-specific Fajr check is genuinely new and needs a Hijri-calendar-aware date range, which nothing in the app currently computes — `PrayerTimesService` gets Fajr's *time*, not the Hijri month boundaries).

## 7. Milestone Celebrations — New, but check this against Achievements first

This is the one place I'd slow down before building. Every example you gave — 100-day streak, 1000 XP, a completion-count threshold — is structurally identical to what the existing Achievement system already does: tiered thresholds (bronze→platinum) over streak/level/totalCompletions/habitMastery/greenSquares, with its own celebration animation already wired through `reaction_overlays.dart`. Building a fully separate "Milestone Celebrations" system risks two parallel places that both decide "did the user just hit 100 days" using two different code paths that can drift out of sync.

I'd extend the Achievement catalog instead — add the specific thresholds you listed (500 green squares, 1000 XP, 10,000 completions, a Quran-specific mastery tier for "1000 Quran pages" via the existing `habitMastery` trigger) as new tiers or new families, rather than a new system. That reuses the detection code, the celebration UI, and the reward pipeline (XP/gold on unlock) all at once. Where a genuinely new mechanism *is* worth adding: the achievement catalog structurally only handles even, curated bronze-to-platinum climbs — the shared Milestone Event Log from section 0 is what gives you an easy way to also mark them on a *timeline* (Journey Page, Legacy Shelf), which today's achievement unlock alone doesn't do — so the real new work here is "make achievement unlocks also write to the shared log," not "build a second celebration system."

## 8. Legacy Shelf — New, near-zero new logic

Every line in your example is either a field that already exists (`longestStreak`, `level`, `createdAt`) or a count query against the Milestone Event Log once it exists (Perfect Weeks ×18). "Lifetime Prayers: 6432" reuses Life Timeline's catalog-based prayer aggregation from section 1 directly — same function, second call site, not a rewrite. This is a new, permanent section in `ProfileScreen`'s existing `CustomScrollView`/slivers structure, not a new screen; lowest-risk item on this whole list.

## Cross-cutting risks worth watching

The category-collapse trap in section 1 applies to *any* future feature that tries to slice stats by category — worth a one-line comment on `HabitCategory.toJson()` itself flagging it, so the next person (or the next Claude session) doesn't rediscover it the hard way. Milestone Event Log write volume needs the "coarse events only" discipline from day one, since Firestore write costs scale with how disciplined that stays. Denormalizing `level` onto `RoomParticipant` means a room's displayed level can go briefly stale between syncs — the exact same accepted tradeoff `characterId`/`displayName` already live with there, not a new category of risk. Animated cosmetics (frames/idle poses) are the one item on this whole roadmap that's blocked on a product/art decision (what rendering approach — Lottie, sprite sheets, shader effects) rather than blocked on engineering time.

## Prioritized build order

**Foundation (build first, unlocks four other items):** the Milestone Event Log — model, the `users/{uid}/milestones` collection, and wiring it into `DashboardNotifier`'s existing level-up/streak/achievement-unlock detection points. Medium effort; nothing downstream of it can be built cleanly without it existing first.

**Tier 1 — ship independently, no new infrastructure, highest visible payoff:** Life Timeline (small-medium; the category-mapping fix is the only real work) and Rooms Phase 1 celebrations (small-medium; pure client-side diffing over streams that already exist) can both start immediately and don't depend on the Milestone Event Log or on each other. Extending the Achievement catalog with the new thresholds from section 7 is small and can happen in parallel.

**Tier 2 — build once the log exists:** Legacy Shelf (small — mostly reads), Journey Page (small-medium — rendering plus the perfect-week/Ramadan-Fajr detection), Monthly Story (medium — reuses Life Timeline's aggregation, adds export/share and the animated-slide UI). I'd do them in that order since each is a superset of the previous one's data needs.

**Tier 3 — needs a product/art decision before engineering finishes:** Level System. Titles and static cosmetics (frames/banners/nameplates) can start now; animated cosmetics wait on a rendering-approach decision.

**Tier 4 — explicitly design-only per your instruction:** Rooms Phase 2 push notifications. Worth writing the Cloud Function + FCM design doc now (cheap, and it should share its "what's celebration-worthy" logic with Phase 1 rather than reinvent it), but not implementing yet.

**Ongoing, not a single ship:** Beautiful Statistics — run as a recurring pass over Progress Hub and Monthly Heatmap as the other tiers land, rather than blocking anything on it.
